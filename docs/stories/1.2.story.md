# Story 1.2: Owner Configuration and Factory Pattern

## Status
Draft

## Story
**As a** test developer,
**I want** Owner-backed configuration and a simple factory pattern,
**so that** object creation is clear and type-safe with minimal overhead.

## Acceptance Criteria
1. Owner interfaces support environment profiles (local, CI).
2. Factory classes are documented with clear creation methods; no static mutable singletons.
3. Example instantiation for API client and UI driver/session via factory methods.

### Configuration Implementation Details
[Source: architecture/data-models.md#Framework Configuration Model]
The Owner library will be used to create type-safe configuration interfaces:
- **BaseConfig**: Root configuration interface in `hex-core/src/main/java/com/company/hex/core/config/`
- **ApiConfig**: API-specific configuration in `hex-core-api/src/main/java/com/company/hex/api/config/`
- **UiConfig**: UI-specific configuration in `hex-core-ui/src/main/java/com/company/hex/ui/config/`

Key Owner annotations to use:
- `@Config.Sources`: Specify property file locations (e.g., `"classpath:hex.properties"`, `"classpath:hex-${env}.properties"`)
- `@Key`: Map property keys to method names
- `@DefaultValue`: Provide default values for optional properties
- `@Config.LoadPolicy(Config.LoadType.MERGE)`: Enable property merging across profiles

[Source: architecture/components.md#hex-core-testing]
ConfigFactory utility requirements:
- Must provide thread-safe, immutable configuration instances
- Located in `hex-core/src/main/java/com/company/hex/core/config/ConfigFactory.java`
- Should throw `HexConfigException` for invalid configurations
- Example method signature: `public static <T extends Config> T getConfig(Class<T> configClass)`

### Factory Pattern Implementation
[Source: architecture/high-level-architecture.md#Key Design Decisions]
Factory Pattern approach:
- Simple, clear mechanism for creating complex objects
- No static mutable singletons - each factory call returns new instance
- Explicit creation over implicit injection (KISS principle)
- Thread-safe by default for parallel execution

[Source: architecture/coding-standards.md#Critical Rules]
Factory implementation requirements:
- Use designated factories (e.g., `ApiServiceFactory`, `WebDriverFactory`)
- Avoid complex object creation logic within test methods
- All public methods must have Javadoc in Russian
- Use `final` fields and immutable objects where possible

### Environment Profiles
[Source: architecture/infrastructure-and-deployment.md#Environments]
Two primary profiles to support:
- **local**: Developer machine, driven by `src/main/resources/hex.properties`
- **ci**: Jenkins environment, driven by `hex-ci.properties` and environment variables

### Security Considerations
[Source: architecture/security.md#Input Validation]
Configuration validation requirements:
- All configuration properties must be validated on startup
- Fail-fast principle: refuse to run with invalid configuration
- ConfigFactory throws `HexConfigException` for missing or malformed properties
- Never hardcode secrets in source code - use Owner configuration interface

### Testing
[Source: architecture/testing-strategy.md]
Testing requirements for this story:
- Unit tests for all factory classes and configuration interfaces
- Test thread-safety of ConfigFactory
- Test immutability of configuration objects
- Mock external dependencies (e.g., mock WebDriver for factory tests)
- Follow AAA pattern (Arrange, Act, Assert)
- Minimum 85% line coverage
- Test files: `*Test.java` in `src/test/java`
- Use JUnit 5 (5.10.2) with Mockito (5.12.0)
