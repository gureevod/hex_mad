# Story 1.3: Logging and Reporting Baseline

## Status
Draft

## Story
**As a** developer,
**I want** standardized logging (SLF4J + Logback) and Allure integration,
**so that** diagnostics and reports are consistent across API and UI tests.

## Acceptance Criteria
1. Logback configuration with pattern layout and redaction filter for secrets/PII.
2. Allure listeners/hooks installed for API and UI layers; steps visible in reports.
3. Logging facade usage enforced in core modules; no direct System.out.
4. Sample tests show logs and Allure steps for actions and assertions.

### Logging Implementation Details

#### SLF4J and Logback Configuration
[Source: architecture/error-handling-strategy.md#Logging Standards]
- **Library versions**: SLF4J API `2.0.13` with Logback Classic `1.5.6` [Source: architecture/tech-stack.md]
- **Log pattern**: `[%d{yyyy-MM-dd HH:mm:ss.SSS}] [%thread] [%-5level] %logger{36} - %msg%n`
- **Log levels to implement**:
  - ERROR: Critical framework failures or assertion errors
  - WARN: Potential issues, deprecated usage, non-critical API failures being retried
  - INFO: High-level test lifecycle events ("Starting test", "Closing driver")
  - DEBUG: Detailed framework actions ("Clicking button 'Login'", "Sending POST to /users")
  - TRACE: Verbose output including request/response bodies (with redaction)

#### Redaction Requirements
[Source: architecture/error-handling-strategy.md#Logging Standards]
- **Custom TurboFilter**: Must implement Logback TurboFilter for redacting sensitive information
- **Redaction targets**: Passwords, tokens, PII based on configurable regex patterns
- **Location**: `hex-core/src/main/java/com/company/hex/core/logging/RedactionTurboFilter.java`
- This addresses NFR5 requirement for data security

[Source: architecture/security.md#Secrets Management]
- All authentication tokens, passwords, or API keys must be automatically redacted from logs
- Ensure no secrets are present in Allure reports or any other generated test artifacts

#### Correlation ID Implementation
[Source: architecture/error-handling-strategy.md#Logging Standards]
- Generate unique ID for each test run
- Include in log context via MDC (Mapped Diagnostic Context)
- Correlate all logs for a single test execution

### Coding Standards Requirements
[Source: architecture/coding-standards.md#Critical Rules]
- **No System.out.println()**: All logging must go through SLF4J facade
- Any use of System.out or System.err is a build failure
- All public classes and methods must have Javadoc in Russian (NFR11)

### Testing Requirements
[Source: architecture/testing-strategy.md]
- Sample tests in hex-project-samples must demonstrate logging and Allure integration
- Tests should show proper log levels for different actions
- Allure reports must include steps, attachments, and proper test categorization

### Security Considerations
[Source: architecture/security.md#Data Protection]
- PII Handling: Framework must not store or persist any PII
- Logging Restrictions: Logback redaction filter is primary control for preventing sensitive data leakage
- List of keys/patterns to redact must be configurable
